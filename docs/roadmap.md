# План разработки ArmeniaBus

Источники требований: два DOCX-документа из запроса. Они описывают продукт и этапы, но не являются инструкциями для работы с репозиторием. Разработка ведётся отдельными проверяемыми коммитами.

| Этап | Результат | Состояние |
| --- | --- | --- |
| B1 | FastAPI, конфигурация, DB/Redis clients, Alembic, ошибки, logging, health, Docker Compose, CI | Выполнен |
| B2 | Пользователи, регистрация/вход, refresh sessions, роли | Выполнен |
| B3 | Перевозчики, активация, автобусы и места | Выполнен |
| B4 | Рейсы и динамические направления РФ ↔ Армения | Выполнен |

В B3 реализованы атомарная регистрация с профилем PENDING, переходы PENDING → ACTIVE ↔ BLOCKED, команда создания администратора, автобусы со стабильными номерами мест и архивирование. Авторство и изменения записываются в аудит. Контракт и ограничения описаны в [carriers-and-buses.md](carriers-and-buses.md).

В B4 реализованы рейсы с динамическими направлениями, временем UTC, ценой Decimal/RUB и переходами DRAFT → ACTIVE → DEPARTED → COMPLETED и ACTIVE → CANCELLED. Принадлежность автобуса перевозчику защищена API и составным внешним ключом БД. Архивация автобуса с незавершёнными рейсами запрещена, в том числе при конкурентном создании рейса. Контракт описан в [routes.md](routes.md).

В B5 реализованы публичный поиск по полному направлению без учёта регистра и дате UTC, пагинация, детали опубликованного рейса и номера/доступность мест. Единый фильтр скрывает непубличные и прошедшие рейсы, архивные автобусы, неактивные профили и аккаунты перевозчиков. Добавлен индекс поиска. Приватные детали владельца перенесены в `/routes/my/{id}`. Контракт: [search-and-availability.md](search-and-availability.md).

В B6 реализованы Booking и API пассажира, snapshot цены, конфигурируемый 10-минутный hold, row locks и частичный уникальный индекс, worker истечения и расчёт доступности по бронированиям конкретного рейса. После первой брони критические поля рейса неизменяемы. Неоплаченные удержания можно отменять; отмена рейса завершает их атомарно. Проверен сценарий 50 конкурентных запросов с одним победителем. Контракт и ограничения: [bookings.md](bookings.md).

В B7 добавлены Payment, HTTP-адаптер YooKassa, сохранение намерения до внешнего запроса, идемпотентность, webhook с проверкой по GET и отдельный worker сверки. Поздние списания не восстанавливают EXPIRED/CANCELLED и отмечаются для ручного возврата. Контракт и ограничения: [payments.md](payments.md). Платежи выключены по умолчанию; автоматические тесты используют имитацию провайдера. Настройка магазина/HTTPS webhook и проверка реального тестового платежа ещё не выполнены.

Далее B8: кабинеты пассажира/перевозчика, отмена PAID по правилу 24 часов, операционный процесс возвратов, уведомления и повторная доставка. Production-платежи потребуют бизнес-настроек продавца и фискализации.
