# Платежи — B7

Интеграция реализована для redirect-оплаты YooKassa с `capture: true`. По умолчанию `PAYMENTS_ENABLED=false`: API не отправляет запросы провайдеру и не создаёт демонстрационные PAID. Локальные автоматические тесты используют имитацию провайдера; проверка с настоящим тестовым магазином и публичным webhook выполняется отдельно после настройки доступа.

## API

`POST /api/v1/bookings/{id}/pay` требует токен владельца-пассажира и заголовок `Idempotency-Key: <UUID>`. Тело отсутствует или равно `{}`: сумма, валюта, магазин и return URL определяются сервером. Ответ `200` содержит `id`, `booking_id`, `status`, `amount`, `currency`, `confirmation_url`, `review_reason`, `created_at`.

Для повторов используйте **тот же ключ**. На одну бронь создаётся одно платёжное намерение. Другой ключ для той же брони или повтор ключа для другой брони того же пассажира возвращает `409 IDEMPOTENCY_CONFLICT`. После FAILED/CANCELED новый платёж для этой брони не создаётся: нужно завершить старую бронь и выбрать место заново. Успешный повтор не продлевает hold.

`GET /api/v1/bookings/{id}/payment` показывает собственный платёж. Чужой и отсутствующий возвращают одинаковый `404 PAYMENT_NOT_FOUND`. Ссылка подтверждения выдаётся только для PENDING без отметки разбирательства и с ещё действующим HELD. Статус Payment и Booking различается: факт списания может быть SUCCEEDED, хотя бронь уже истекла и требует возврата.

Основные ошибки: `410 HOLD_EXPIRED`, `409 PAYMENT_NOT_AVAILABLE`, `503 PAYMENTS_DISABLED`, `503 PROVIDER_UNAVAILABLE`. При таймауте/503 нельзя автоматически создавать новую бронь и повторять списание с новым ключом: запрос мог дойти до провайдера. Сохраните ключ, прочитайте платёж и повторите с тем же ключом, пока hold действует.

## Идемпотентность и сбои

До HTTP-запроса транзакция сохраняет Payment PENDING, snapshot суммы и неизменяемый JSON запроса. В YooKassa передаётся внутренний UUID Payment в `Idempotence-Key`. Изменение настроек return URL между попытками не меняет уже сохранённый запрос. Запрос выполняется без открытой транзакции/блокировок БД.

Если ответ потерян, тот же запрос повторяется с тем же ключом; если внешний ID уже известен, используется только GET статуса. Новые POST запрещены после окончания hold, отмены брони либо через 23 часа от создания намерения. Это консервативный предел внутри 24-часового окна идемпотентности провайдера. Неизвестный результат после истечения срока получает `UNKNOWN_RESULT_REQUIRES_REVIEW`, а не предполагаемый FAILED. [Правила идемпотентности и неопределённость HTTP 500 в YooKassa](https://yookassa.ru/developers/using-api/interaction-format).

Подтверждённое отклонение POST с HTTP 400/422 сохраняется как FAILED. Таймауты, 429, 5xx, неверные ответы и ошибки доступа не считаются доказательством отсутствия списания. Полные ответы и HTTP-ошибки провайдера не записываются в аудит; карточные поля ответа отбрасываются адаптером.

## Webhook и подтверждение

`POST /api/v1/webhooks/payments` принимает `type=notification`, событие `payment.succeeded`, `payment.canceled` или `payment.waiting_for_capture`, и `object.id`. Тело уведомления не задаёт статус, сумму или связь с бронью. Backend получает объект через authenticated GET YooKassa и сверяет внешний ID, сумму, валюту, магазин, test/live и metadata с сохранённым намерением. Проверка по GET — один из способов проверки подлинности, описанных [YooKassa](https://yookassa.ru/developers/using-api/webhooks).

Metadata из проверенного GET позволяет обработать webhook, пришедший раньше ответа на создание. Неизвестные чужие платежи игнорируются. Корректно обработанное уведомление получает HTTP 200; временная невозможность проверить провайдера — 503 для повторной доставки. Статус из frontend redirect никогда не подтверждает оплату.

После GET блокируются профиль перевозчика → рейс → Booking → Payment, строки перечитываются. Только `succeeded` с `paid=true` и полностью совпавшими реквизитами может перевести ещё действующий HELD на доступном рейсе в PAID. Обновления и аудит фиксируются одной транзакцией. Повторы и устаревшие события не возвращают терминальный платёж в PENDING и не создают повторное событие оплаты.

Если деньги пришли после истечения/отмены hold либо рейс/перевозчик стал недоступен, Payment становится SUCCEEDED с `REFUND_REQUIRED`. Booking не восстанавливается, а место другого пассажира не затрагивается. С B8 в той же транзакции создаются заявка RefundCase и уведомление; автоматического refund нет. Заявки доступны ADMIN через `/admin/refund-cases`, с B9 оператор записывает результат ручного возврата через `/admin/refund-cases/{id}/record`. Проверка неопределённого платежа только через GET провайдера доступна в `/admin/payments/{id}/verify`: [операционный контракт](admin-operations.md). Расхождение реквизитов даёт `PROVIDER_DATA_MISMATCH`; неожиданное ожидание capture — `UNEXPECTED_CAPTURE_REQUIRED`. Эти случаи требуют проверки и не подтверждают бронь. Подробнее: [cabinets-and-notifications.md](cabinets-and-notifications.md).

## Worker сверки

`payment-worker` работает независимо от worker истечения hold. Он выбирает просроченные по `next_check_at` PENDING, атомарно назначает следующий опрос и проверяет провайдера. По умолчанию интервал 30 секунд, batch 10. Повтор после сбоя безопасен; сетевое ожидание не удерживает row locks. Отмеченные для ручного разбора записи автоматически не повторяются, но verified webhook может зафиксировать позднее списание.

Разовая сверка: `docker compose run --rm payment-worker python -m armeniabus.modules.payments.worker --once`. В выключенном режиме worker не делает HTTP-запросов. Параметры `PAYMENT_POLL_SECONDS` и `PAYMENT_BATCH_SIZE` поддерживаются приложением; при изменении Compose передайте их в environment сервиса.

## Подключение тестового магазина

Предварительная проверка конфигурации и доступа без создания платежа, а также сценарии приёмки: [staging-integrations.md](staging-integrations.md).

В локальном `.env` задаются `PAYMENTS_ENABLED=true`, `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `YOOKASSA_TEST_MODE=true`, `PAYMENT_RETURN_URL`. Ключ не передаётся через API пассажира и не коммитится. `test_mode` проверяет поле `test` ответа; сам режим магазина определяется выданными YooKassa ключами.

Сначала собрать `api worker payment-worker`, применить `alembic upgrade head`, затем перезапустить сервисы. Для уведомлений понадобится доступный YooKassa HTTPS URL `/api/v1/webhooks/payments` и настройка событий в кабинете магазина. Сам localhost для внешних webhook недоступен. Return URL ведёт на frontend `/payment/result`; при создании Payment backend добавляет `booking=<UUID>`, сохраняя адрес в payload для повторов. Страница читает состояние API, не доверяя параметрам успеха: [frontend-payments.md](frontend-payments.md). Origin возврата должен совпадать с адресом открытого frontend, чтобы сохранить браузерную сессию и доступ к ключу попытки.

Перед включением реального магазина нужны согласованная модель продавца/расчётов, настройки чеков/фискализации и процесс ручного возврата. Передача `receipt` пока не реализована; магазины, требующие чек в запросе, отклонят такой платёж. Это граница текущей интеграции, а не готовность к production-приёму денег. Для live-конфигурации backend требует HTTPS return URL.

## Проверки

Аудит цепочки покупки и новые регрессионные сценарии:
[локальная приёмка покупки](qa/2026-10-28-purchase-audit.md).
Локальный `FAILED` после отказа POST может быть исправлен поздним совпадающим
verified `succeeded/paid=true`; истёкшая бронь при этом не восстанавливается.
Конфликт уже терминального статуса снимается только явной проверкой администратора
при совпадении актуального состояния. Пометка возврата этой операцией не снимается.

Покрыты HTTP-контракт адаптера, точная сумма, сохранённый ключ/тело после таймаута, повторные запросы и webhook, поддельное тело уведомления, несоответствие суммы/валюты/магазина/test/metadata, ранний webhook, поздняя оплата с повторно занятым местом, отмена провайдером, права доступа, истечение hold и worker без webhook. Реальные запросы YooKassa и списания в автоматических тестах не выполняются.
