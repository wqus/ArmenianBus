# Бронирование и удержание в браузере — F5

После выбора места ссылка ведёт на `/trips/{route_id}/book?seat={seat_id}`. Для продолжения нужен активный PASSENGER. Вход/регистрация сохраняют только разрешённый внутренний адрес с валидными UUID; после входа место проверяется заново. Создание брони требует отдельного нажатия «Удержать место». Переход, reload и восстановление сессии сами не отправляют POST.

## Создание и восстановление

`POST /api/v1/bookings` передаёт только UUID рейса и места. Пассажир, цена, срок и статус определяются backend. Синхронный guard и disabled-состояние защищают от двойного нажатия; API-клиент не повторяет мутации автоматически, даже после обновления токена. Успех открывает защищённый `/bookings/{id}`. Уход со страницы во время запроса не отменяет возможную запись на сервере и не возвращает пользователя назад после позднего ответа.

При `BOOKING_CONFLICT` предлагаются повторный выбор и просмотр своих броней. При timeout, сетевой ошибке, 5xx или неожиданном успешном ответе интерфейс не утверждает, что брони нет: POST может уже завершиться. Кнопка повторного создания скрывается; пользователь переходит в `/bookings`, обновляет список и открывает сохранённую бронь. Серверной идемпотентности создания Booking по-прежнему нет. Новая ручная попытка при активном удержании этого места защищена уникальным ограничением БД.

Список `/bookings` читает существующий `/cabinet/bookings`, показывает последние брони со статусом и переходом к деталям. Пагинация использует 20 видимых записей и один lookahead, максимум offset 10000. Список добавлен для восстановления незавершённого сценария; расширенный кабинет с фильтрами и историей операций относится к F7.

## Таймер и состояние

Детали берутся из `/cabinet/bookings/{id}`, поэтому направление, место и сумма доступны и после закрытия публичного рейса. Сумма — сохранённая цена Booking, а не повторно вычисленная цена из поиска. Неавторизованный пользователь получает вход, чужая бронь — одинаковое с отсутствующей состояние 404. Query cache разделён по пользователю и очищается при завершении/смене сессии.

В CabinetBooking добавлено `server_time` — время SQL statement, которым прочитаны бронь и её эффективный статус. Схема БД не менялась. Остаток рассчитывается из `held_until - server_time`; полностью вычитается время запроса как консервативная поправка. Далее используется `performance.now()`, чтобы изменение часов устройства не продлевало удержание. Таймер обновляется раз в секунду, статус HELD — каждые 15 секунд в видимой вкладке и при возвращении в неё. Отказ чтения скрывает старые детали и действия, доступны ручное обновление и восстановление при возвращении во вкладку.

Ноль на клиентском таймере не присваивает EXPIRED: интерфейс сообщает о проверке срока и ждёт ответа сервера. При EXPIRED таймер исчезает; новое удержание создаётся только явным действием после выбора места. PAID/COMPLETED отображаются только по данным API. Переход к оплате и результат реализованы в [F6](frontend-payments.md).

## Отмена

Для HELD предлагается «Отменить удержание» с подтверждением и возможностью сохранить бронь. Frontend отправляет `DELETE /bookings/{id}?hold_only=true`. После результата, включая потерю ответа, статус перечитывается; CANCELLED не назначается локально. При неизвестном результате пользователь видит сообщение и актуальный результат последующего GET.

Новый необязательный `hold_only` сохраняет прежнее поведение API по умолчанию. При `true` проверка выполняется под блокировкой Booking: PAID/COMPLETED возвращают `409 BOOKING_NOT_HELD` до возвратов или других изменений. CANCELLED/EXPIRED остаются идемпотентными. Это не позволяет кнопке отмены неоплаченного удержания отменить билет, который успели оплатить в другой вкладке.

## Проверки и запуск

Backend-тесты проверяют серверное время, эффективное истечение, отмену/повтор и отказ hold-only после подтверждённого платежа без возврата. Frontend unit-проверки покрывают контракт брони, монотонный таймер, задержку ответа и разрешённые адреса возврата после входа.

Браузерные сценарии: вход к выбранному месту, один POST, reload, отмена/сохранение, потерянный ответ и восстановление из списка, конфликт, запрет CARRIER, нулевой таймер до серверного EXPIRED, ошибки GET/404, PAID в гонке отмены, axe и мобильная вёрстка. Live E2E расширяет сценарий F3/F4 настоящим созданием и отменой в браузере, затем имитирует истечение только синтетической брони в проверенной БД `armeniabus_test`. Тестовые деньги/письма наружу не отправляются.

Подготовка и очистка отдельного Compose project — [browser-auth.md](browser-auth.md). Поскольку изменился контракт кабинета, при локальном обновлении нужен новый backend: `docker compose build api` и `docker compose up -d --no-deps api`. Выполнять миграцию для F5 не требуется. Публичный production-запуск не выполнялся.
