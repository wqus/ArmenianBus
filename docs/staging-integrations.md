# D3: подготовка платёжной и почтовой интеграций

Сервер, домен и доступы ещё не предоставлены; этап выполняется локально. Добавлена команда `python -m armeniabus.integration_check`, входящая в API-образ. Она не создаёт платежи, не отправляет письма, не читает и не изменяет БД. Проверки с имитацией провайдеров не заменяют приёмку настоящего тестового магазина и почтового ящика.

## Что проверяет команда

Без флагов выполняется только анализ эффективных настроек приложения: hardened-режим `APP_ENV=production`, совпадение HTTPS origin возврата, CORS и разрешённого host, путь `/payment/result`, test mode, наличие ключей магазина и согласованность настроек SMTP. Текстовый JSON-отчёт содержит только фиксированные коды и статусы; значения ключей, адрес отправителя, ответы провайдеров и пароли не печатаются. `scope=configuration_only` означает, что соединения не проверялись.

При `--network` и успешных проверках конфигурации выполняются:

- `GET https://api.yookassa.ru/v3/me` с серверной авторизацией. Проверяются совпадение account ID, `test=true`, статус магазина и параметры фискализации. Для включённой передачи чеков возвращается `RECEIPT_SUPPORT_NOT_IMPLEMENTED`: текущий payload платежа не содержит `receipt`. Параметр `fiscalization.enabled` имеет приоритет над устаревшим `fiscalization_enabled` согласно [спецификации API ЮKassa](https://yookassa.ru/developers/using-api/openapi-specification).
- SMTP over TLS: проверка сертификата, EHLO, авторизация при наличии пары username/password, NOOP. Команды MAIL/RCPT/DATA не вызываются. Это проверка подключения, а не доставки писем.
- HTTPS GET `/api/v1/health/ready` на настроенном origin. Требуются корректный сертификат, ответ 200 и `{"status":"ok"}`. Redirect автоматически не выполняется.

HTTP-запросы имеют таймауты и не используют proxy-переменные окружения. SMTP использует тот же протокол `SMTP_SSL`, что и обработчик уведомлений; STARTTLS/587 пока не поддерживается. Проверка не меняет `PAYMENTS_ENABLED`/`NOTIFICATIONS_ENABLED` и может проверять соединения до включения этих переключателей. При любой ошибке конфигурации все сетевые проверки пропускаются. Отсутствие чеков в настройках API не подтверждает готовность бизнеса к приёму денег.

Код выхода 0 означает успех только запрошенной области проверки; 1 — есть блокирующая ошибка. В отчёте всегда остаётся `acceptance_complete=false` до отдельной ручной приёмки, которую эта команда не подтверждает. Если API магазина не разрешает `GET /me`, это блокирующий результат, а не повод считать магазин проверенным или делать пробное списание автоматически.

## Локальная проверка сейчас

```powershell
.venv/Scripts/python.exe -m armeniabus.integration_check
.venv/Scripts/python.exe -m pytest tests/test_integration_check.py -q
```

В текущем development-окружении первая команда ожидаемо возвращает 1: staging и внешние доступы ещё не настроены. Она не требует запуска Docker/БД и не подключается к сети. Не включать реальные интеграции для устранения этого ожидаемого результата. Рабочий `.env` не менялся.

## После появления staging

1. Создать отдельное окружение по [environments.md](environments.md), развернуть проверенный выпуск по [releases.md](releases.md). Использовать синтетические аккаунты и рейсы; не копировать production-пользователей и очередь уведомлений.
2. В защищённом env-файле сервера заполнить shop ID и секрет **тестового** магазина, SMTP host/port/from и авторизацию. Оставить оба переключателя интеграций выключенными. `.env.staging.example` показывает имена параметров; секреты не передавать в Git, командной строке или чатах.
3. После применения конфигурации выполнить проверку внутри API-контейнера (путь к `active.env` нужен после D2-обновления):

```sh
docker compose -p armeniabus-staging -f compose.production.yaml --env-file /secure/staging.env --env-file release-state/staging/active.env exec -T api python -m armeniabus.integration_check
docker compose -p armeniabus-staging -f compose.production.yaml --env-file /secure/staging.env --env-file release-state/staging/active.env exec -T api python -m armeniabus.integration_check --network
```

4. Настроить внешний webhook `/api/v1/webhooks/payments` в тестовом магазине. Успешный GET readiness не доказывает доступность webhook со стороны провайдера. Выполнить приёмочные сценарии ниже, включая настоящий webhook.
5. Перед включением уведомлений проверить состав PENDING/FAILED-очереди: worker обработает накопленные письма. Использовать только согласованные тестовые адреса. Перед первым реальным письмом требуется явно выбранный получатель и разрешение на отправку.

## Приёмка после подключения

| Сценарий | Ожидаемый результат |
| --- | --- |
| Успешная тестовая оплата | Payment SUCCEEDED и действующая бронь PAID только после проверенного ответа провайдера |
| Возврат на сайт до webhook | Страница ждёт подтверждения; redirect сам по себе не меняет бронь |
| Повтор запроса/уведомления | Одно платёжное намерение, без повторных бизнес-событий |
| Отмена платежа | Отражён ответ провайдера, бронь не становится PAID |
| Задержка подтверждения до истечения hold | Бронь не восстанавливается; при списании открыт случай ручного возврата |
| Потерянный webhook | Worker сверяет статус по API; сверка видна в кабинетах и аудите |
| Подтверждение/отмена брони | Письмо приходит в согласованный ящик, корректны маршрут, время UTC и номер места |
| Ошибка SMTP и повтор | Статус ошибки и повтор обработаны; SENT не выдаётся до принятия письма SMTP-сервером |

Для каждого сценария сохранить версию выпуска, время, UUID синтетической брони/платежа, результат и очищенные от секретов свидетельства. Повтор письма при неопределённом SMTP-результате возможен: стабильный Message-ID не гарантирует exactly-once доставку. Автоматического перечисления возвратов и поддержки receipt в этом этапе не добавлено.

Следующие независимые локальные работы: подготовка внешнего мониторинга/оповещений и расписания защищённых резервных копий. Полностью закрыть D3 можно после появления staging, ключей магазина и SMTP и прохождения настоящей приёмки.

Проверка локального этапа: 32 новых теста диагностики прошли отдельно; полный backend-прогон в Docker/Python 3.12 — 195 passed без пропусков, с PostgreSQL/Redis и миграциями 0001–0010. Тестовый Compose project удалён. Ruff, формат новых Python-файлов, staging Compose config и Git diff check проходят. Команда доступна в собранном образе; локальный запуск без сети корректно сообщает об отсутствующей staging-конфигурации. Проверки провайдеров используют имитацию HTTP/SMTP; настоящие запросы с ключами и отправка писем не выполнялись.
