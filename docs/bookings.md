# Бронирования и удержание — B6

## API пассажира

Все операции требуют Bearer token активного `PASSENGER`. Другие роли получают `403`, чужая и отсутствующая бронь одинаково возвращают `404 BOOKING_NOT_FOUND`.

- `POST /api/v1/bookings` — создать удержание (`201`). Тело: `{"route_id": "UUID рейса", "seat_id": "UUID места"}`.
- `GET /api/v1/bookings/my?limit=20&offset=0` — собственные брони, сначала новые, порядок `created_at DESC, id DESC`. Limit 1–100, offset 0–10000.
- `GET /api/v1/bookings/{id}` — собственная бронь, включая историю.
- `DELETE /api/v1/bookings/{id}` — отменить неоплаченное удержание (`204`). Повтор для CANCELLED/EXPIRED безопасен.

Клиент не передаёт пассажира, цену, срок удержания или статус. Неизвестные поля возвращают `422`. Ответ содержит `id`, `route_id`, `seat_id`, `bus_id`, `status`, `amount`, `currency`, `held_until`, `created_at`. Деньги сериализуются десятичной строкой, например `"4500.50"`; время — ISO 8601 UTC.

Booking хранит snapshot цены рейса. После любой первой брони, включая EXPIRED/CANCELLED, редактирование автобуса, направления, времени и цены через обычный PATCH рейса возвращает `409 ROUTE_HAS_BOOKINGS`. История не удаляется.

## Транзакция и ограничения БД

Бронировать можно только будущий ACTIVE рейс с неархивным автобусом, активным перевозчиком и активным аккаунтом владельца. Место обязано принадлежать автобусу этого рейса. Составные внешние ключи Booking → Route/Seat дополнительно защищают это соответствие.

Порядок блокировок создания: профиль перевозчика → рейс → автобус → Seat → существующий активный Booking. Редактирование/отмена рейса и архивация автобуса используют совместимый порядок. В MVP это сериализует изменения одного перевозчика; при масштабировании гранулярность блокировок можно сузить, сохранив инварианты.

Частичный уникальный индекс `(route_id, seat_id) WHERE status IN ('HELD', 'PAID')` исключает вторую активную бронь даже при обходе сервисного кода. Одно статическое место автобуса можно независимо забронировать на разных рейсах. Занятое место возвращает `409 BOOKING_CONFLICT`; клиент должен обновить схему мест.

После получения блокировок время читается из PostgreSQL через `clock_timestamp()`. Просроченный HELD того же места переводится в EXPIRED, затем создаётся новая бронь — в одной транзакции. Срок новой брони: минимум из `now + BOOKING_HOLD_MINUTES` и времени отправления. По умолчанию hold равен 10 минутам, настройка допускает 1–60 минут. Рейс после отправления возвращает `409 ROUTE_NOT_BOOKABLE`.

Повтор POST после успешного запроса возвращает конфликт, если место ещё удерживается. Отдельного механизма идемпотентного повторения POST booking пока нет; при потере ответа клиент может найти свою бронь через `/bookings/my`. Идемпотентность платежа относится к B7.

## Доступность и истечение

В публичных деталях, поиске и `/seats` состояние вычисляется по Booking конкретного рейса:

- PAID занимает место независимо от старого `held_until`.
- HELD занимает место только пока `held_until` позже времени БД.
- EXPIRED, CANCELLED и просроченный HELD не занимают место.

Колонки `Seat.status` нет. Каждый публичный запрос читает согласованный снимок одним SQL statement; свежесть не зависит от Redis. Поиск показывает число свободных мест; рейс с нулём свободных мест остаётся в выдаче с `free_seats: 0`.

Чтение собственной брони также показывает эффективный статус EXPIRED сразу после срока. Пока worker не обработал строку, её сохранённый статус может ещё быть HELD: GET не выполняет запись. Новое бронирование на это место само завершит старый hold. Время `held_until` остаётся источником истины.

Worker выбирает ограниченный batch просроченных HELD через `FOR UPDATE SKIP LOCKED`, переводит их в EXPIRED и пишет аудит в той же транзакции. Несколько процессов могут работать одновременно. Повтор не создаёт новые события и не меняет PAID. После ошибок БД worker повторяет обработку; завершённые транзакции сохраняются. При перезапуске он продолжает со строками PostgreSQL.

```powershell
docker compose build api worker
docker compose run --rm api alembic upgrade head
docker compose up -d api worker
# Один batch с кодом завершения 0/1:
docker compose run --rm worker python -m armeniabus.worker --once
```

Настройки: `BOOKING_HOLD_MINUTES=10` у API, `HOLD_WORKER_INTERVAL_SECONDS=5` и `HOLD_WORKER_BATCH_SIZE=500` у worker. Worker не подключается к Redis; общие настройки приложения требуют REDIS_URL/JWT_SECRET_KEY, но worker не использует их для принятия решений. Готовность worker в этом этапе проверяется его процессом, журналом и запуском `--once`; отдельного health endpoint/метрик задержки пока нет.

## Отмена и границы этапа

Отмена непросроченного HELD переводит его в CANCELLED и освобождает место. Просроченный HELD при отмене переводится в EXPIRED. Отмена рейса атомарно завершает его неоплаченные удержания. При завершении рейса PAID переводятся в COMPLETED.

На B6 нет `/bookings/{id}/pay`, Payment и webhook; никакой публичный endpoint не позволяет назначить PAID. Интеграционные тесты создают PAID напрямую только в изолированной тестовой БД, чтобы проверить будущие защитные правила. Отмена PAID пассажиром пока возвращает `409 BOOKING_NOT_CANCELLABLE`, отмена рейса с PAID — `409 ROUTE_HAS_PAID_BOOKINGS`.

Платежи и подтверждение PAID относятся к B7. Отмена оплаченного билета с конфигурируемым ограничением 24 часа, операционная отмена рейса, уведомления и ручной процесс возврата относятся к следующим этапам. B7 обязан сохранить порядок блокировок и повторно проверять статус/срок после блокировки Booking; нельзя восстанавливать EXPIRED/CANCELLED в PAID или считать redirect доказательством оплаты.

## Проверки

Тесты покрывают 50 конкурирующих POST с одним успешным результатом и 49 конфликтами, независимость от Redis, ограничение БД при прямом INSERT, принадлежность места, ownership/RBAC, snapshot цены, настройки TTL и отправление, запоздалый/повторный worker, два worker одновременно, бронирование без ожидания worker, доступность разных рейсов одного автобуса, гонки с редактированием цены и отменой рейса.
