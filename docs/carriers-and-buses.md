# Перевозчики и автобусы — этап B3

Этап позволяет перевозчику зарегистрироваться, получить активацию от администратора и управлять собственными автобусами. Пользовательские интерфейсы будут подключены на этапах F2/F8; текущий контракт доступен через FastAPI OpenAPI `/docs`.

## Регистрация и профиль

`POST /api/v1/auth/register` принимает:

```json
{
  "email": "carrier@example.com",
  "password": "choose-a-unique-password",
  "role": "CARRIER",
  "company_name": "Название перевозчика",
  "phone": "+37499123456"
}
```

Ответ `201` содержит пользователя. Пользователь и профиль `PENDING` сохраняются атомарно. Профиль доступен после входа через `GET /api/v1/carriers/me`. Для пассажира поля компании и телефона при регистрации не передаются. Email уникален без учёта регистра; при дубликате возвращается `409 EMAIL_EXISTS`.

Аккаунты перевозчиков, созданные до B3, могут не иметь профиля. Для них предусмотрен `POST /api/v1/carriers/me` с `company_name` и `phone`: `201` при создании, `409` при повторе. Одновременные запросы не создают дубликаты. `PATCH /api/v1/carriers/me` принимает одно или оба этих поля, пока профиль `PENDING`. Пустые значения, `null`, неизвестные поля и попытки изменить статус отклоняются.

## Администратор и активация

Команда `python -m armeniabus.cli create-admin --email admin@example.com` создаёт новую административную учётную запись и запись аудита. Пароль вводится дважды через скрытый prompt. Для автоматизации предусмотрен `--password-stdin`; пароль не выводится в ответ и не передаётся аргументом процесса. При занятом email команда завершается с ошибкой и не меняет роль или пароль существующего пользователя. Самостоятельная регистрация Admin через HTTP запрещена.

`GET /api/v1/admin/carriers?status=PENDING&limit=20&offset=0` возвращает страницу профилей. `PATCH /api/v1/admin/carriers/{id}/status` принимает `{"status":"ACTIVE"}` или `{"status":"BLOCKED"}`. Допустимы `PENDING → ACTIVE`, `ACTIVE → BLOCKED` и `BLOCKED → ACTIVE`. Повтор текущего статуса безопасен и не создаёт дополнительное событие. Недопустимый переход возвращает `409 INVALID_CARRIER_TRANSITION`.

## Автобусы и места

| Метод и путь | Поведение |
| --- | --- |
| `POST /api/v1/buses` | Принимает `name` и целую `capacity` от 1 до 100; создаёт автобус и места `1..capacity`, возвращает `201` и список мест |
| `GET /api/v1/buses` | Страница своих неархивных автобусов: `items`, `limit`, `offset` |
| `GET /api/v1/buses/{id}` | Свой автобус и места с постоянными UUID |
| `PATCH /api/v1/buses/{id}` | Меняет `name`, сохраняя вместимость и идентификаторы мест |
| `DELETE /api/v1/buses/{id}` | Архивирует автобус, возвращает `204`, сохраняет его и места в БД |

Вместимость и нумерация фиксируются при создании. Для другой схемы создаётся новый автобус. Места не хранят изменяемый статус занятости: на B5/B6 он будет вычисляться из бронирований конкретного рейса. На B4 появится проверка действующих рейсов при архивации автобуса.

Все операции с автобусами доступны только пользователям роли `CARRIER` с активным профилем и активной учётной записью. Чужой, отсутствующий или архивный автобус возвращает одинаковый `404 BUS_NOT_FOUND`. Перевозчик не может передать чужой `carrier_id` при создании. Блокировка профиля и изменения автобусов сериализуются блокировкой одной строки профиля в БД: операция, начинающаяся после зафиксированной блокировки, не может изменить автобус.

Списки имеют стабильную сортировку по времени создания и UUID; `limit` ограничен 100. Ошибки валидации возвращаются в едином формате с `code`, `message`, `request_id`, `details`. HTTP-контракт содержит схемы запросов, ответов и ошибок.

## Аудит и проверки

Создание администратора, создание/изменение профиля, смена статуса и изменения автобусов записываются в `audit_log` вместе с бизнес-изменением. В событиях нет паролей, токенов и платёжных данных. HTTP-просмотр журнала относится к B9.

Интеграционные тесты проверяют активацию и блокировку, изоляцию владельцев, генерацию и сохранность мест, архивирование, аудит, валидацию регистрации, запрет повышения прав через bootstrap и конкурентное создание профиля для аккаунта B2. Они выполняются на отдельной тестовой БД с миграциями с нуля.
