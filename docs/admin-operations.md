# Администрирование и операции (B9)

Это backend API для роли ADMIN. UI администратора будет реализован на этапе F9. Администратор создаётся только локальной командой `python -m armeniabus.cli create-admin`; API не повышает роли и не создаёт административные аккаунты.

## Просмотр

Все пути ниже начинаются с `/api/v1/admin`. Нужен Bearer access token активного ADMIN. Без токена — 401, другая роль или заблокированный аккаунт — 403. Отсутствующий UUID возвращает 404.

| GET | Фильтры |
| --- | --- |
| `/users`, `/users/{id}` | `role`, `status` |
| `/carriers`, `/carriers/{id}` | `status` |
| `/routes`, `/routes/{id}` | `carrier_id`, `status` |
| `/bookings`, `/bookings/{id}` | `route_id`, `passenger_id`, `status` |
| `/payments`, `/payments/{id}` | `booking_id`, `status`, `review_required` |
| `/refund-cases`, `/refund-cases/{id}` | `status=OPEN|REFUND_RECORDED` |
| `/notifications`, `/notifications/{id}` | `booking_id`, `status=PENDING|SENT|FAILED` |
| `/audit` | `entity_type`, `entity_id`, `actor_user_id`, `action` |

Списки возвращают `items`, `limit`, `offset`; limit 1–100, по умолчанию 20, offset 0–10000. История пользователей/броней/платежей/уведомлений/аудита сортируется от новых записей к старым с UUID как вторым ключом. Рейсы — по отправлению от новых к старым; перевозчики и возвраты — от старых к новым. Администратор видит архивные рейсы и записи заблокированных перевозчиков. EXPIRED рассчитывается по времени БД даже до обработки hold worker.

DTO пользователей не содержит password hash или refresh-сессий. Платёжный DTO не возвращает request payload, ключ идемпотентности, ссылку подтверждения или реквизиты магазина. DTO уведомления содержит состояние очереди, но не адрес получателя, текст письма или lease token. Audit API доступен только для чтения; запись связана с транзакцией соответствующего действия.

## Блокировка

`PATCH /users/{id}/status` принимает `{"status":"BLOCKED","reason":"Причина решения"}` или ACTIVE. Причина обязательна (1–500 символов после удаления пробелов по краям). Повтор текущего статуса не создаёт аудит повторно. Поле role и другие незаявленные поля запрещены.

Блокировка отзывает все refresh-сессии. Вход и запросы с access token запрещены, пока пользователь BLOCKED; старый refresh token не заработает после разблокировки. Login/refresh сериализуются с блокировкой пользователя, чтобы конкурентный вход не оставил активную refresh-сессию. Access tokens остаются краткоживущими JWT: после разблокировки ещё не истёкший access token снова допускается; постоянного token blacklist в B9 нет. ADMIN-аккаунты защищены от изменения этим API, включая собственный аккаунт.

Статусы аккаунта и профиля перевозчика независимы: разблокировка пользователя не активирует PENDING/BLOCKED CarrierProfile. Существующее `PATCH /carriers/{id}/status` управляет профилем. Блокировка аккаунта перевозчика сериализуется с бронированием и подтверждением платежа через блокировку профиля, затем пользователя. Платёж, подтвердившийся после блокировки, не выдаёт PAID и попадает в ручной возврат.

## Операционная отмена рейса

`POST /routes/{id}/cancel` с `{"reason":"Причина отмены"}` отменяет ACTIVE рейс, в том числе заблокированного перевозчика. Используется тот же транзакционный процесс, что и в API перевозчика: удержания завершаются, оплаченные брони отменяются, создаются заявки на ручной возврат и outbox. Повтор CANCELLED безопасен. Другие состояния дают 409. Критические поля рейса, сумма платежа и статус брони произвольно через Admin API не редактируются.

## Проверка неопределённого платежа

`POST /payments/{id}/verify` принимает `{}` для известного external_id или `{"external_id":"UUID из кабинета провайдера"}` для потерянного результата создания. Отсутствующий внешний ID — `409 EXTERNAL_ID_REQUIRED`; подмена уже сохранённого ID — 409. API выполняет только GET у провайдера и **никогда не создаёт новое списание**. Требуются включённые платежи и исходные магазин/test-mode.

Запрос проверки записывается в аудит до HTTP; сеть не удерживает транзакцию. Ответ проходит общую проверку ID, магазина, режима, metadata, суммы и валюты. Расхождение оставляет платёж на проверке; действительный совпавший ответ может разрешить прежнее неопределённое состояние. Терминальные состояния не откатываются. Поздний SUCCEEDED не восстанавливает истёкшую/отменённую бронь, а создаёт RefundCase. Ошибка провайдера возвращает 503, а не предполагаемую успешную оплату. `review_required=true` показывает оставшиеся исключения; изменение суммы или принудительное подтверждение оплаты API не поддерживает.

## Запись ручного возврата

После выполнения **полного** возврата вне ArmeniaBus администратор вызывает `POST /refund-cases/{id}/record` с `{"reference":"Номер операции возврата"}`. Reference обязателен, до 100 ASCII-символов (буквы, цифры, `. _ : / -`), уникален среди заявок. Частичные возвраты и отмена записи через это API не поддерживаются.

Это административная запись результата ручной операции: API не перечисляет деньги и не проверяет факт зачисления у банка/провайдера. Статус намеренно называется `REFUND_RECORDED`. Сохраняются номер, время PostgreSQL и администратор. Payment остаётся SUCCEEDED; отметка REFUND_REQUIRED снимается, другие причины проверки сохраняются. Бронь PAID/COMPLETED нельзя закрыть возвратом без предварительной отмены; оставшийся HELD позднего платежа завершается атомарно.

Повтор той же операции с тем же reference безопасен и не создаёт второй аудит. Другой reference для уже закрытой заявки или номер другой заявки дают 409. В кабинете пассажира появляются `refund_status=REFUND_RECORDED` и `refund_required=false`; это отметка оператора, а не автоматическая банковская верификация. Повтор payment webhook не открывает заявку заново.

## Повтор доставки

`POST /notifications/{id}/retry` принимает `{"expected_generation":0,"reason":"Исправлена конфигурация SMTP"}`. Текущее поколение берётся из DTO уведомления. Только FAILED без действующей lease переводится в PENDING; attempts сбрасывается, поколение увеличивается, причина и прежнее число попыток остаются в аудите. Одновременный или устаревший повтор получает 409. PENDING и SENT не переотправляются этим API.

Worker отправит письмо позже, только если `NOTIFICATIONS_ENABLED=true`. Стабильный Message-ID сохраняется, однако риск дубля после принятия письма SMTP и сбоя процесса остаётся: доставка at least once. Не записывайте секреты в reason/reference. В текущем локальном окружении SMTP и платежи выключены; автоматические тесты не отправляют настоящие письма и не выполняют списания/возвраты.

## Миграция и проверки

Миграция 0009 добавляет состояние/реквизиты ручного возврата и поколение повтора уведомления. Существующие заявки становятся OPEN, уведомления получают поколение 0. Проверка downgrade/upgrade выполняется только на тестовой БД: откат 0009 удаляет реквизиты записанных возвратов, поэтому для рабочего окружения нужны backup и заранее выбранная процедура восстановления.

Тесты проверяют RBAC и DTO, фильтры/пагинацию, блокировку и отзыв refresh, защищённые ADMIN-аккаунты, оплату во время блокировки перевозчика, административную отмену, конкурентную запись возврата, уникальность номера, повтор webhook, повторную доставку с проверкой поколения, восстановление неопределённого платежа только через GET и ошибки провайдера. Следующий этап B10 — безопасность, наблюдаемость, проверка запросов и резервного восстановления, production-конфигурация.
