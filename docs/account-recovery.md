# Восстановление доступа и подтверждение почты

Вход содержит ссылку «Забыли пароль?». Пассажир или перевозчик запрашивает
письмо, открывает одноразовую ссылку и вводит новый пароль дважды. После успешной
смены потребуется обычный вход; автоматически новая сессия не создаётся.
Профиль показывает, подтверждён ли email, и позволяет запросить письмо.
При включённой почте первое подтверждение также ставится в очередь при регистрации.

## API и ссылки

- `POST /api/v1/auth/forgot-password` — `{email}`, одинаковый ответ 202 для
  доступного, отсутствующего и заблокированного аккаунта. Минимальное время
  ответа выравнивается; действуют ограничения IP/идентичности через Redis.
- `POST /api/v1/auth/reset-password` — `{token, password}`, 204 без выдачи сессии.
- `POST /api/v1/auth/web/reset-password` — тот же сброс с проверкой Origin и
  `X-ArmeniaBus-Web: 1`, дополнительно удаляет HttpOnly refresh-cookie.
- `POST /api/v1/auth/verification/request` — запрос подтверждения собственного
  адреса; требуется действующий bearer. Ответ 202 не означает доставку письма.
- `POST /api/v1/auth/verify-email` — `{token}`, явное подтверждение, 204.

Восстановление действует 30 минут, подтверждение — 24 часа. Проверка срока
использует время PostgreSQL после получения блокировок. Неверная подпись,
истёкшая, использованная ссылка и недоступный аккаунт дают один `ACTION_LINK_INVALID`.
Ссылки разных назначений не взаимозаменяемы. GET ничего не подтверждает и не меняет:
сканер почты не должен расходовать ссылку вместо человека.

Секрет передаётся во фрагменте `#token=...`, который не отправляется HTTP-серверу.
Интерфейс переносит его в память формы и удаляет из адресной строки/истории до POST.
Секреты не записываются в web storage и не вставляются в DOM. Новая ссылка в той же
вкладке создаёт новую форму; повторное открытие страницы без ссылки не повторяет POST.
При потерянном ответе на сброс предлагается проверить вход с новым паролем или
запросить новую ссылку, а не повторять неизвестный результат автоматически.

## Сессии и конкурентные операции

Миграция `0014` добавляет `users.auth_version`, `email_verified_at` и приватную
таблицу `auth_actions`. Сброс блокирует пользователя, затем действие, помечает
ссылку использованной, обновляет Argon2-хеш пароля, увеличивает версию авторизации
и отзывает все refresh-сессии и остальные ссылки сброса этого пользователя.
Запоздалый вход, успевший проверить старый хеш до блокировки, также отклоняется.

Bearer JWT содержит версию. Существующие JWT без этого поля принимаются только
при версии аккаунта 0: обновление схемы не выкидывает всех пользователей, но сброс
сразу лишает старые JWT доступа. Два одновременных использования ссылки имеют
одного победителя. Смена пароля не меняет роль, блокировку и активацию перевозчика.

Подтверждение email сохраняет `email_verified_at`; в других открытых вкладках
статус обновляется через существующий канал сессии без передачи токенов.
Старые адреса не объявляются подтверждёнными автоматически. На пилотном этапе
отсутствие подтверждения не блокирует существующие бронирования и оплату.

## Приватная очередь и SMTP

Обычная очередь уведомлений о брони не хранит ссылки восстановления. В `auth_actions`
хранятся случайный UUID4, назначение, хеш секрета, срок, получатель и состояние доставки.
Сам секрет — 256-битный HMAC от случайного идентификатора и назначения с отдельным
контекстом протокола на серверном ключе. URL и тело письма создаются только в памяти
отправителя; bearer-ссылка не лежит открытым текстом в БД, аудите или списке писем админа.
Снимок получателя связан с действием: при несовпадении текущего email ссылка не действует.

Один запрос письма на аккаунт/назначение допускается не чаще минуты, максимум пять
за час. Остальные запросы дают тот же общий ответ. Новый запрос не отменяет ранее
отправленные ссылки: злоумышленник не должен мешать восстановлению повторными запросами.

Существующий notification-worker обслуживает обе очереди. Используются блокировки
`SKIP LOCKED`, lease на 120 секунд, идентификатор владельца lease, ограниченные повторы
и SMTP over TLS. В ошибку пишется только тип исключения, без SMTP-ответа и получателя.
Протухшие/использованные действия не отправляются. При смене серверного ключа старые
ссылки недействительны, неотправленные письма получают `TOKEN_KEY_CHANGED`; нужна новая
ссылка. Записи старше 30 дней после истечения удаляются ограниченными batch по 100.

Доставка почты допускает повтор после сбоя подтверждения SMTP, но повторная ссылка
не может второй раз изменить аккаунт. После смены пароля отдельное письмо сообщает
о событии без нового пароля и без bearer-ссылки. Оно ставится в очередь даже при
временно отключённой доставке.

## Конфигурация и локальная проверка

Дополнительные аккаунты провайдера или новые ключи не требуются: используется тот
же SMTP и `NOTIFICATIONS_ENABLED`. При выключенной доставке запрос нового письма
возвращает 503 `ACCOUNT_MAIL_UNAVAILABLE`; интерфейс сообщает о недоступности почты.
Ранее выданную действующую ссылку всё ещё можно использовать.

`AUTH_PUBLIC_ORIGIN` — необязательный точный origin без пути, query, fragment и
credentials. По умолчанию берётся origin `PAYMENT_RETURN_URL`. Production Compose
задаёт HTTPS origin из `APP_DOMAIN` автоматически для API и worker. HTTP Host из
запроса не используется для формирования ссылок. В production требуется HTTPS.

Backend-проверки используют FakeSender. В api-e2e включена очередь с `smtp.invalid`,
но SMTP-worker этого проекта не запускается: сквозной тест читает только собственное
синтетическое письмо из проверенной БД `armeniabus_test`, проходит весь UI и проверяет
отзыв сессий. Настоящие письма и платежи автоматическими тестами не отправляются.
Реальную доставку этих двух новых шаблонов нужно принять на целевом SMTP отдельно.

[Отчёт локальной проверки](qa/2026-10-28-account-recovery.md) содержит результаты
автотестов и ограничения приёмки.

Подход к одноразовым ссылкам, общим ответам и отзыву сессий сверялся с
[OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).
