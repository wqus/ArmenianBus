# Кабинет пассажира — F7

`/bookings` показывает собственные брони, предстоящие поездки и историю с данными оплаты/возврата. Доступ — PASSENGER; профиль `/account` содержит переход в кабинет. Используется существующий API B8/B9, новых endpoint и миграций нет.

## Список и фильтры

«Все», «Предстоящие», «История» соответствуют серверному `segment=all|upcoming|history`. Дополнительный `status` фильтрует эффективный статус Booking. Предстоящие поездки определяются серверным временем, ACTIVE рейсом и действующим HELD/PAID. Клиент не вычисляет историю по часам устройства и не подменяет серверный EXPIRED.

Фильтры хранятся в URL вместе с offset: `/bookings?segment=history&status=CANCELLED&offset=20`. Изменение фильтра сбрасывает offset. Навигация назад/вперёд, reload и вход сохраняют выбранный список. Разрешены только известные параметры, по одному значению; offset — кратный 20 в диапазоне 0–10000. Неверный URL показывает восстановление к общему списку без запроса с другими фильтрами. Redirect после входа формируется из проверенных значений, произвольный `next` не принимается.

Страница запрашивает 21 запись, показывает 20 и использует последнюю как признак следующей страницы. Сортировка — серверная, от новых броней к старым. Это offset-пагинация, а не снимок данных: параллельно созданная бронь может сдвинуть границу страниц. Query key содержит пользователя и все фильтры, запросы используют AbortSignal. При смене фильтров/ошибке старые карточки скрываются. История здесь — список бронирований с текущим состоянием; отдельная хронология всех событий API пассажиру не предоставляется.

Карточки показывают направление, время отправления UTC, место, перевозчика, сумму snapshot, состояние брони, платежа и возврата. В деталях дополнительно видны дата создания и состояние рейса. Проверка контракта требует известные `route_status`, `payment_status`, `refund_status` и согласованность `refund_required` с OPEN. Неизвестный/повреждённый ответ скрывает данные и действия.

## Отмена

Кнопка оплаченной отмены появляется только для PAID с серверным `cancellation_allowed=true`. Перед DELETE пассажир подтверждает именно отмену оплаченной брони и создание заявки на ручной возврат. «Сохранить бронь» закрывает подтверждение без запроса. Удержание и оплаченная бронь имеют разные подтверждения; смена статуса не превращает уже открытое подтверждение HELD в разрешение отменить PAID.

HELD отправляет `DELETE /bookings/{id}?hold_only=true`, PAID — `DELETE /bookings/{id}`. Сервер повторно проверяет срок/рейс под блокировками; frontend не зашивает порог 24 часа, поскольку он настраивается. `CANCELLATION_CUTOFF` и `BOOKING_NOT_CANCELLABLE` объясняются пользователю. При `cancellation_allowed=false` для PAID отображается недоступность отмены.

Синхронный guard предотвращает двойное нажатие; автоматического повтора DELETE нет. После успеха или неопределённого ответа бронь перечитывается, а кэш списков/доступности/платежа обновляется. CANCELLED и возврат не назначаются оптимистически. Ошибка последующего GET скрывает старые действия. Повторное открытие страницы восстанавливает состояние по API.

## Платёж и возврат

SUCCEEDED остаётся фактом подтверждённого платежа после отмены. OPEN показывается как открытая заявка на ручной возврат. REFUND_RECORDED — «Возврат отмечен оператором»: это запись оператора, а не банковское подтверждение поступления денег. Тексты общие для кабинета и страницы результата оплаты. Если Payment требует REFUND_REQUIRED, но кабинет ещё не содержит заявки, сохраняется сообщение о необходимости проверки.

Детали брони обновляются каждые 15 секунд для HELD/PAID/OPEN, страница оплаты — каждые 5 секунд для HELD/PENDING/OPEN. Опрос выполняется в видимой вкладке, доступен refresh при фокусе и вручную; ошибка останавливает периодический опрос. Письма и автоматическое перечисление возвратов этим этапом не включаются.

## Проверки

Unit: фильтры, границы пагинации, безопасный возврат после входа, runtime-контракт финансовых состояний, различие OPEN/REFUND_RECORDED. Browser E2E desktop/mobile: фильтры/URL/reload/назад, пустой список, ошибки и поздний ответ, подтверждение/отказ отмены PAID, двойное нажатие, потерянный ответ, deadline, повреждённый DTO, смена HELD → PAID, состояние возврата на странице оплаты, axe и адаптивная вёрстка.

Live E2E в отдельном Compose project проверяет историю реальных синтетических отменённых броней, фильтрацию, пустой результат и reload. Оплаченная отмена/возврат проверяются браузерными mock-сценариями и существующими backend integration-тестами с FakeProvider, включая конкурентную отмену, cutoff и запись ручного возврата. Внешних списаний/писем нет. Рабочая БД не заполняется тестовыми данными.
