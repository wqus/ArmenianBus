# Оплата в браузере — F6

Пассажир открывает `/bookings/{id}/payment` из своей брони. Страница сначала читает `GET /bookings/{id}/payment`, затем актуальную бронь из кабинета. Вход сохраняет адрес возврата; роль PASSENGER обязательна. Чужая бронь не раскрывается. Цена берётся из snapshot, контракт и совпадение суммы/идентификатора проверяются на клиенте.

## Подготовка и переход

Только явное нажатие «Подготовить оплату» отправляет `POST /bookings/{id}/pay`, без суммы, карточных данных и return URL. Перед POST повторно читаются платёж и действующее удержание. Синхронный guard блокирует двойной клик; автоматического повтора мутации нет. После ответа, включая потерянный, клиент перечитывает платёж и бронь. POST payload не используется как подтверждение оплаты.

Ключ UUID сохраняется до отправки в localStorage, отдельно для пользователя и брони; Web Locks сериализует получение ключа между вкладками одного origin. При перезагрузке и ручном повторе используется тот же ключ. Это не токен доступа: в хранилище находятся только идентификаторы пользователя/брони/попытки. Ключ не удаляется при выходе, чтобы повторный вход не создавал другую попытку. Очистка браузерного хранилища утрачивает ключ; для уже существующего PENDING без ссылки новый ключ не создаётся. Другая вкладка/устройство может продолжить по полученной из API ссылке, но без исходного ключа не повторяет подготовку. Ошибка сохранения блокирует POST. Backend остаётся окончательной защитой от дубликатов и конфликтов.

При действующем HELD и PENDING без `review_reason` показывается ссылка «Перейти на страницу ЮKassa». Автоматического внешнего перехода после позднего ответа нет. Разрешён только HTTPS на точном `yoomoney.ru`, без credentials и нестандартного порта; lookalike host, javascript, HTTP и protocol-relative адреса отклоняются. Ссылка передаётся только API и открывается в той же вкладке с `noreferrer`. При изменении провайдером хоста список нужно пересмотреть по его официальному контракту. [Redirect-сценарий ЮKassa](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process).

## Возврат и состояние

Backend добавляет `booking=<UUID>` к настроенному `PAYMENT_RETURN_URL` при создании намерения, заменяя старые значения этого параметра и убирая fragment. URL сохраняется в неизменяемом payload Payment; повтор не меняет его при смене конфигурации. Рекомендуемый путь — `https://<frontend>/payment/result`, в локальном окружении — `http://localhost:5173/payment/result`. Используйте один и тот же origin для frontend и return URL: cookie и localStorage привязаны к origin. Изменять уже созданные намерения не требуется.

`/payment/result?booking=UUID` читает собственную бронь, включая после входа или открытия на другом устройстве. Query-параметры `status`, `success` и подобные не подтверждают оплату. Пустая/неверная/дублированная booking-ссылка ведёт к выбору брони, а не угадывает последнюю попытку. Старые намерения без booking в return URL также восстанавливаются из списка своих броней.

Проверка GET повторяется раз в 5 секунд для HELD/PENDING и открытой заявки на возврат в видимой вкладке, при фокусе и вручную. Чтение не запускает provider POST; backend worker/webhook проверяет YooKassa. Ошибка скрывает устаревшие действия и останавливает периодический опрос до ручной проверки/фокуса. Нулевой серверный таймер скрывает переход к оплате, но не назначает локальный EXPIRED.

Только SUCCEEDED вместе с PAID/COMPLETED и без отметки разбора показывают «Оплата подтверждена». С F7 состояние возврата читается из кабинета: OPEN — открытая заявка, REFUND_RECORDED — запись оператора о ручном возврате. Она не означает банковскую проверку поступления денег. При наличии заявки действия оплаты скрыты. Если Payment требует REFUND_REQUIRED, но кабинет не содержит заявки, интерфейс предлагает уточнить результат в поддержке. Прочие отметки разбора сообщают о проверке. PENDING, отсутствие платежа, CANCELED/FAILED и недоступная бронь имеют отдельные состояния. Для FAILED/CANCELED нельзя создавать новое намерение на ту же бронь. PAYMENTS_DISABLED отображается явно; локальные настройки автоматически не включаются.

## Проверки и запуск

Unit-тесты проверяют redirect URL, контракт Payment, отделение оплаты от брони/возврата, сохранение ключа и маршруты входа. Browser E2E (desktop/mobile Edge) проверяет двойной клик, перезагрузку, две вкладки, потерю ответа, вход после возврата, чужую бронь/роль, выключенную оплату, ошибки GET, истечение, позднее списание, небезопасную ссылку, отказ хранилища, axe и адаптивную вёрстку. Провайдер и API в этих сценариях перехвачены; реальных списаний нет.

Backend integration проверяет booking в payload и сохранение идентичного payload после timeout/смены настройки; прежние проверки идемпотентности/webhook/гонок остаются обязательными. Live browser E2E дополнительно проверяет PAYMENTS_DISABLED на настоящем API в изолированной БД: Payment не создаётся, удержание сохраняется, пассажир возвращается к своей брони и отменяет её. Миграций F6 нет. Обновление локального API: `docker compose build api`, `docker compose up -d --no-deps api`. Настройка магазина/HTTPS webhook и настоящий тестовый платёж — отдельная проверка по [payments.md](payments.md).
