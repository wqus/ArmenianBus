# Поиск и доступность — B5

Публичные endpoints не требуют токена:

- `GET /api/v1/routes/search?origin=Ростов-на-Дону&destination=Гюмри&date=2030-06-01`
- `GET /api/v1/routes/{id}`
- `GET /api/v1/routes/{id}/seats`

Для будущего рейса доступны только статус `ACTIVE`, неархивный автобус, активный профиль перевозчика и активный аккаунт владельца. Один фильтр видимости используется для всех трёх операций. Скрытый и отсутствующий рейс одинаково возвращают `404 ROUTE_NOT_FOUND`. Публичный ответ не включает email, телефон, данные авторизации и пассажиров.

## Поиск

Обязательные параметры: `origin`, `destination`, `date`. Названия точек обрезаются по краям и сравниваются целиком без учёта регистра средствами PostgreSQL. Это не поиск подстроки: `%` и `_` не являются шаблонами. Города не зашиты в код; поддерживаются направления в обе стороны. Транслитерация, исправление опечаток и объединение разных написаний города не выполняются.

`date` — календарный день **UTC**: интервал от 00:00 включительно до 00:00 следующего дня исключительно. Часовой пояс не выводится из названия города. Например, `2030-06-02T01:00:00+03:00` попадает в поиск за `2030-06-01`. Интерфейс должен явно обозначать эту семантику; поиск по местной дате потребует отдельного контракта часовых поясов. Прошедший день возвращает пустой список.

`limit` по умолчанию 20, допустимо 1–100; `offset` по умолчанию 0, допустимо 0–10000. Порядок — `departure_at`, затем UUID. Пагинация не фиксирует снимок между запросами: новые публикации и отмены могут изменить следующие страницы. Ответ: `{"items": [...], "limit": 20, "offset": 0}`. Пустая выдача — `200` с `items: []`.

Элемент выдачи и публичные детали содержат поля рейса, `company_name`, `bus_name`, `capacity`, `free_seats`. Цена остаётся десятичной строкой RUB, время — UTC. Неизвестные параметры, пустые названия, неправильная дата и выход за границы пагинации возвращают стандартный `422 VALIDATION_ERROR`.

## Места

Ответ `/seats`:

```json
{
  "route_id": "UUID рейса",
  "bus_id": "UUID автобуса",
  "free_seats": 2,
  "seats": [
    {"id": "UUID места 1", "seat_number": 1, "status": "FREE"},
    {"id": "UUID места 2", "seat_number": 2, "status": "FREE"}
  ]
}
```

Места отсортированы по номеру. UUID берутся из статических мест автобуса. Статус вычисляется при чтении, колонка `Seat.status` не добавляется. На B5 бронирований ещё нет, поэтому все существующие места имеют `FREE`; число свободных мест считается по строкам мест, а не подставляется из вместимости автобуса.

Контракт предусматривает `FREE`, `HELD`, `PAID`. На B6 расчёт будет учитывать Booking конкретного рейса и `held_until` в PostgreSQL. До реализации B6 показ свободного места не резервирует его, продажи ещё не открыты. После B6 окончательное решение о бронировании будет приниматься транзакцией, а не результатом предыдущего поиска.

Каждый публичный запрос читает рейс, видимость и доступность одним SQL statement. Redis cache не используется. Миграция `0005` добавляет частичный индекс опубликованных неархивных рейсов по `lower(origin)`, `lower(destination)`, `departure_at`, `id`.

## Изменение контракта B4

`GET /api/v1/routes/{id}` теперь публичный. Владельцу для просмотра собственных черновиков, отменённых и завершённых рейсов следует использовать новый `GET /api/v1/routes/my/{id}` с Bearer token. Список `/routes/my` и операции `POST/PATCH/DELETE` сохраняют прежние права и адреса. Чужие приватные рейсы остаются недоступными.

## Проверки

Интеграционные тесты проверяют поиск кириллицей и армянскими названиями, точные цены, границы дня UTC, стабильный порядок при одинаковом отправлении, пагинацию, буквальную обработку шаблонов/SQL-строк, одинаковую видимость поиска/деталей/мест, блокировку профиля и аккаунта, архивирование, отсутствие приватных полей и сохранность доступа владельца.
